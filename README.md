# GTR Manager

GTR Manager is the package manager component of GTR.

It is responsible for:

- Project initialization
- Dependency management
- Script execution
- Workspaces (families of packages developed together)

GTR Manager is executed by the `gtr` launcher. End users normally interact only with the `gtr` command.

# Installation

You normally don't install GTR Manager yourself: `gtr` installs the version a
project asks for (`"engines": {"gtr": "^0.2"}` in `gtr.json`) from the GitHub releases
of this repository and runs it. All commands below work as `gtr <command>` and as
`gtr-manager <command>`.

```bash
gtr self install gtr 0.2      # install explicitly
gtr self list gtr             # installed versions
gtr-manager version
```

Working on GTR Manager itself — use your build instead of releases:

```bash
go build -o build/gtr-manager ./cmd/gtr-manager
gtr self link gtr ./build/gtr-manager
gtr self unlink gtr           # back to releases
```

## Releases

`gtr version patch && gtr publish` tags `v1.2.3` and pushes it. The tag runs
`.github/workflows/release.workflow.yml`: tests, then gtr-manager builds itself
(`gtr-manager build --all-targets --archive`, the `build` block of `gtr.json`):
`gtr-manager_<version>_<os>_<arch>.zip|tar.gz` for Windows, Linux and macOS
(amd64, arm64) plus `SHA256SUMS`, published as a GitHub release. `gtr`
refuses archives that don't match `SHA256SUMS`.

## Development

```bash
go vet ./... && go test ./...      # unit tests; some use the go command and the module cache
make build                         # build/<version>/<os>-<arch>/gtr-manager (gtr build)
make release                       # every platform, archives and SHA256SUMS
```

Design decisions are in the gtr repository: `docs/adr`.

# Project Manifest

Every project has a `gtr.json` (schema: `gtr/schema/gtr.schema.json`):

```json
{
    "name": "blog",
    "version": "1.0.0",
    "engines": { "go": ">=1.22", "gtr": "^0.2" },
    "dependencies": {
        "orm": "github:shibisty/orm.go#^0.1",
        "orm-mysql": "github:shibisty/orm.go-mysql-driver#^0.1",
        "github.com/google/uuid": "^1.6",
        "passport": "file:../passport.go/core"
    },
    "devDependencies": {
        "faker": "github:shibisty/faker.go#^0.1"
    },
    "scripts": {
        "start": "go run .",
        "build": "go build ./...",
        "test": "go test ./..."
    }
}
```

The key of a dependency is its **import path** — `import "orm"`, `import "orm/schema"`,
`import mysql "orm-mysql"`, `import "github.com/google/uuid"` — and the value says where it
comes from (ADR-0003). Package names are lowercase letters, digits and single hyphens
(ADR-0002); keys with a dot are external Go modules.

Other fields: `peerDependencies` (packages the application must provide, e.g. the core of
a driver), `workspaces` (see [Workspaces](#workspaces)), `private`, `description`,
`license`, `repository`, `"gomod": "commit"`.

Files written by older versions are migrated automatically, with a warning:
`"github:owner/repo": "*"` becomes `"<name>": "github:owner/repo"`, `"engine"` becomes
`"engines": {"go": …}`, `"website"` becomes `"homepage"`, and `"entrypoint"` is dropped.

## What `gtr install` produces

| File | What it is | Commit it? |
|---|---|---|
| `gtr.lock` | Exact versions, commits and `h1:` hashes of every package | **Yes** |
| `gtr_modules/<name>` | Links (junctions on Windows) into `~/.gtr/store` | No (`.gitignore`) |
| `go.mod` | Generated from `gtr.json`; Go tools and IDEs read it | No, unless `"gomod": "commit"` |

The generated `go.mod` starts with a hash of its content. If you edit it by hand, gtr
stops: `gtr sync` carries the edit over to `gtr.json` (a new `require` of a module → a
dependency with a range, a changed version → a new range, a removed `require` → the
dependency is removed, `replace <package> => ../dir` → a `file:` source) and regenerates
the file; `gtr sync --force` discards it. `go mod tidy` leaves the file unchanged.

### Existing Go projects

```bash
gtr init       # keeps the module path as the name when it is a valid gtr name
gtr sync       # imports go.mod: requires → dependencies, go directive → engines.go
```

`gtr sync` keeps the module versions written in `go.mod`, so the build list does not move.
A gtr name has no dots (ADR-0002); if the module path was `github.com/me/app`, imports of
the project's own packages change to `app/...`.

### Running go

Scripts (`gtr run`) and the `go` shim run go with `GOPROXY=off`, `GOWORK=off` and
`-mod=mod` when the project's `go.mod` was generated by gtr: every dependency is already in
`gtr_modules/`. go errors get a line from gtr saying what to do:

```
main.go:5:2: package orm is not in std (/usr/local/go/src/orm)
gtr: package "orm" is not installed: add it with `gtr add github:owner/repo` (or `gtr add file:../path`); if it is already in gtr.json, run `gtr install`
```

Hints are not added when stderr is a terminal and the command runs your program (`go run`,
or any `gtr run` script), so the program still sees a terminal.

Package names that are taken by the Go standard library (`errors`, `log`, …, from
`go list std` of the active Go) are rejected by `gtr init` and `gtr install`.

### The store

Downloaded packages live once per version in `~/.gtr/store` and are shared by all
projects; a package directory is never modified after it is stored. Each stored package
gets a generated `go.mod` (`module <name>`), so published packages don't need one.

# Commands

## Create a project

```bash
gtr new blog                       # asks a few questions; -y accepts the defaults
gtr new blog -t cli                # from a template (--template)
gtr init [name] [-y]               # gtr.json in the current directory
```

| Template | What you get |
|---|---|
| `app` (default) | `main.go` with a test; scripts `start`, `build`, `test` |
| `cli` | a command-line tool: flags, `-version` set at build time, a testable `run()` |
| `lib` | a library package with a test and an example, version 0.1.0 |
| `orm-driver` | an orm driver on `database/sql`: peer `orm ^0.1`, the shared `orm/drivertest` suite as an integration test |
| `fullstack` | a web application on the fullstack framework: SQLite, users with registration and login, migrations, seeders, views, HTTP tests; `go run . list` shows its console commands |
| `none` | `gtr.json` and `.gitignore` only |

`init` writes `gtr.json` and adds `gtr_modules/`, `go.mod` and `go.work` to `.gitignore`.
The package name becomes the import path, so it must be a valid name.

## Add packages

```bash
gtr add github:shibisty/orm.go                    # newest tag, saved as "^0.1"
gtr add github:shibisty/orm.go#^0.1               # a range
gtr add github:owner/repo/packages/http           # a package in a monorepo subdirectory
gtr add file:../passport.go/core                  # a local package, linked in place
gtr add -D github:shibisty/faker.go               # devDependencies
gtr add orm=github:shibisty/orm.go                # fail unless the package is named "orm"
gtr add gitlab:group/project                      # GitLab (GTR_GITLAB_URL for a self-hosted one)
gtr add git+https://git.example.com/team/lib.git  # any git server (also git+ssh://, git+file://)
gtr add orm                                       # in a workspace member: another member
```

The package name is read from the package's own `gtr.json`; it must match the key
(ADR-0003), so a repository cannot pose as another package.

**Versions come from git tags**: `v1.2.3` or `1.2.3` for the repository root;
`<name>@1.2.3` or `<subdir>/v1.2.3` for a monorepo subdirectory. A repository without
version tags can still be used with `*`: gtr takes the tip of the default branch and
pins its commit in `gtr.lock` (version `0.0.0-g<commit>`). Such a version satisfies peer
ranges (`"orm": "^0.1"`), so packages can depend on each other before their first release,
but not dependency ranges.

## The gtr registry

Packages published to a gtr registry ([gtr-registry](https://github.com/shibisty/gtr-registry)) are
added by their name:

```bash
gtr add greet                         # saved as "greet": "^0.1" (the newest version)
gtr add greet@^0.1.0
gtr search greet
gtr info greet                        # description, owners, versions
```

The registry sends each version's gtr.json and the SHA-256 of its archive; gtr-manager checks the
archive on download, keeps it in the store, and records `"source": "registry:<url>"` and the
checksum in `gtr.lock`. A yanked version is skipped by new installs and updates, but a project
whose gtr.lock has it keeps installing it. `--offline` works from the store.

The registry is `GTR_REGISTRY`, else the one of the last `gtr login`, else `http://localhost:4873`
(a gtr-registry running locally, until a public one exists). Publishing:

```bash
gtr login                             # email and password (or --token gtr_...), saved in ~/.gtr/registry.json
gtr publish                           # checks, tests, then the archive
gtr yank greet@0.1.1                  # --undo brings it back
gtr owner add greet bob@example.com   # owner greet | owner remove greet <email>
gtr logout
```

`GTR_REGISTRY_TOKEN` gives a token in CI (make one on the registry's dashboard).

## npm packages (frontend)

Frontend packages come from the npm registry, without npm or Node.js:

```bash
gtr add npm:preact                    # saved as "npm:^10.19.3"
gtr add npm:@preact/signals@^1.2
```

```json
"dependencies": {
    "preact": "npm:^10.19"
}
```

They go into `node_modules/` (added to `.gitignore`), where esbuild (fullstack-bundler) and editors
find them; they never reach `go.mod`. Versions follow npm's range rules (`^`, `~`, `x`, `||`,
`1.2 - 2.0`; the `latest` tag first), and dependencies are hoisted like npm does: a second version
of a package goes into its dependent's own `node_modules`. Tarballs are checked against the
registry's `integrity` hash and kept in `~/.gtr/store/npm`; `gtr.lock` records every package (its
`npm` section), and `gtr ci` installs exactly that. **Install scripts never run**: packages that
need a `postinstall` step (native addons) are not supported. A gtr package can declare `npm:`
dependencies too; they are installed into the project's `node_modules`.

`GTR_NPM_REGISTRY` points to another registry (a mirror, Verdaccio), `GTR_NPM_TOKEN` is its bearer token.

## External Go modules

Regular Go modules are keyed by their module path:

```bash
gtr add github.com/go-sql-driver/mysql            # newest tag, saved as "^1.8.1"
gtr add github.com/redis/go-redis/v9@~9.7.0       # a range
```

```json
"dependencies": {
    "github.com/go-sql-driver/mysql": "^1.8"
}
```

gtr picks the highest version the range allows (like `go get`: retracted versions are
skipped, `+incompatible` ones used only as a last resort), then applies minimal version
selection over the modules' own `go.mod` files until nothing changes — the same build
list the go command computes for the generated `go.mod`. Gtr packages can depend on Go
modules the same way in their own `gtr.json`.

A range admits newer versions that may need a newer Go: pgx 5.11 needs Go 1.25, for example.
A library that supports an older Go (ADR-0007: 1.22) pins a patch range such as `"~5.7.1"`
and tests the minimum Go in CI; the generated `go.mod` gets the highest `go` line of what
was selected.

| Variable | Meaning |
|---|---|
| `GTR_GOPROXY` | Module proxy (default: first `http(s)` entry of `GOPROXY`, else proxy.golang.org) |
| `GTR_GOPROXY_PRIVATE` | Proxy for `GOPRIVATE`/`GONOPROXY` modules; private paths never go to the public proxy |
| `GTR_GOSUMDB` | Checksum database URL or `off` (default: from `GOSUMDB`, else sum.golang.org) |
| `GONOSUMDB`, `GOPRIVATE` | Modules not looked up in the checksum database |

Every `go.mod` and zip is checked: against `gtr.lock` when the module is locked (no
network needed, like `go.sum`), otherwise against the checksum database. Modules are
unpacked into `~/.gtr/store/go` and linked as `gtr_modules/.go/<module>@<version>`;
`go.sum` is not needed, and `go mod tidy` is not either — `gtr install` does its job.

Known limits: the transparency-log inclusion proof that the go command also checks is
not verified yet; every module of the build list is downloaded, including ones whose
packages are never imported (the go command downloads only `go.mod` for those).

## Install

```bash
gtr install                 # everything from gtr.json, keeping versions from gtr.lock
gtr update                  # newest versions the ranges allow, for all packages
gtr update orm              # only orm
gtr ci                      # exactly gtr.lock; fails if it does not match gtr.json
gtr sync                    # carry go.mod edits (or an existing go.mod) over to gtr.json
gtr sync --force            # regenerate go.mod, discarding manual edits
```

One version of each package is selected for the whole project. If two packages need
incompatible versions, gtr explains who requires what:

```
no version of orm satisfies all requirements:
  the project requires orm ^0.2
  orm-mysql@0.1.0 requires orm ^0.1
available versions: 0.2.0, 0.1.3, 0.1.0
```

`peerDependencies` (a driver needing a core package) are not installed automatically;
gtr fails with a hint if the project lacks a compatible version. A package lists its core
both as a peer (`"orm": "^0.1"`, what the application must provide) and as a
devDependency (`"orm": "github:shibisty/orm.go"`, so its own tests build).

Downloads run in parallel. `--offline` (or `GTR_OFFLINE=1`) works without the network:
`gtr install --offline`, `gtr ci --offline`, `gtr add --offline …` use only what the
store (`~/.gtr/store`) and the module cache already have, in the versions they have, and
fail with "not available offline" for anything else.

If a tag was moved after you locked it (force-pushed to another commit), gtr refuses to
install until you run `gtr update <name>`. `gtr ci` also re-hashes the stored packages,
so a file changed through `gtr_modules/` is caught.

## Inspect

```bash
gtr list                    # direct dependencies (of every member in a workspace)
gtr list --tree             # everything; --depth 2 for two levels; --json
gtr why strutil             # which requirements bring it in
gtr outdated                # newer versions of direct dependencies; --all: of everything
```

```
Package        Current  Wanted  Latest  Source
orm            0.1.3    0.1.5   0.2.0   github:shibisty/orm.go
faker (dev)    0.1.0    0.1.0   0.2.0   github:shibisty/faker.go
```

*Wanted* is the newest version all ranges allow — what `gtr update` installs; for *Latest*
change the range (`gtr add github:shibisty/orm.go#^0.2`). `list` and `why` read
`gtr.lock` and need no network.

## Run scripts

```bash
gtr run                     # the "start" script (or: gtr start)
gtr run build
gtr run test -- -run TestLogin -v   # arguments after -- go to the script
gtr run -r test                     # in every workspace member that has "test"
gtr migrate                         # a script that is not a gtr command runs like `gtr run migrate`
```

Without a script of that name, `gtr run test`, `build`, `dev`, `install` and `ci` run the gtr command
of the same name (with a note). A mistyped script or command gets a suggestion:
`script "tset" is not defined; did you mean "test"?`, ``Did you mean `gtr install`?``.

Scripts run in the directory of the nearest `gtr.json`. `pre<name>` and `post<name>` run
around a script when they are defined (`pretest`, `posttest`); the arguments go to the
script itself. A missing script is an error that lists the available ones. The exit code
of the script is the exit code of `gtr`. Scripts run go with gtr's environment (see
[Running go](#running-go)), so `go test` in a script needs no setup.

Variables from `.env` and `.env.local` (local secrets, not committed) are added to the
script's environment; variables already set in the environment win. In a workspace
member the root's files are read first. `gtr run --no-env <name>` skips them.

```
# .env
DB_HOST=localhost
DB_URL="postgres://app@${DB_HOST}/app"   # ${VAR} and \n work in double quotes
LITERAL='$not_expanded'
```

## Build

```bash
gtr build                       # this platform: build/<version>/<os>-<arch>/<name>
gtr build -t linux/arm64        # one target (repeat -t, or -t linux/arm64,windows/amd64)
gtr build --all-targets         # build.targets, or the six platforms gtr is released for
gtr build --all-targets --archive   # + <name>_<version>_<os>_<arch>.zip|tar.gz and SHA256SUMS
gtr build --version 1.2.0-rc.1  # instead of the version in gtr.json
```

The `build` block of `gtr.json` describes the binary:

```json
"build": {
    "entry": "./cmd/app",
    "output": "app",
    "ldflags": "-s -w -X main.Version={{version}} -X main.Commit={{commit}} -X main.Date={{date}}",
    "tags": ["netgo"],
    "targets": ["linux/amd64", "windows/amd64"],
    "files": ["README.md", "LICENSE", "config.example.yml"]
}
```

`{{version}}`, `{{commit}}` (git, 12 characters), `{{date}}` (UTC, RFC 3339;
`SOURCE_DATE_EPOCH` fixes it) and `{{name}}` are replaced in `ldflags`. Builds use
`CGO_ENABLED=0` (`"cgo": true` to change) and `-trimpath` (`"trimpath": false`), and run
targets in parallel. Archives hold the binary at their root plus `files` (default
`README*`, `LICENSE*`), the layout gtr installs releases from (ADR-0008). In a workspace
root, `gtr build` builds every member that has a `build` block.

`gtr dev` builds the entry, runs it with the `.env` variables and rebuilds and restarts it
whenever a Go file, `gtr.json` or `.env` changes, in the package or any workspace member
(`gtr dev -- --port 8080` passes arguments; a failed build keeps the old process).

## Test

```bash
gtr test                        # go test ./... (-race when cgo and a C compiler are there)
gtr test --integration --e2e    # add the build tags integration, e2e (--unit: none)
gtr test --coverage [--html]    # coverage per package, build/coverage.out (.html)
gtr test --watch                # again on every change
gtr test -r                     # every workspace member, dependencies first
gtr test --run TestLogin -v -- -shuffle=on
```

```json
"test": {"coverage": 70, "race": true, "timeout": "5m"}
```

With `test.coverage`, `gtr test --coverage` fails below that percentage (`--min 80`
overrides it). `build.tags` apply to tests too.

## Release

```bash
gtr version                     # orm-mysql 0.1.0
gtr version patch               # 0.1.0 → 0.1.1 (minor, major, 2.0.0, prerelease --preid rc)
gtr publish --dry-run           # the checks only (and the files of the archive)
gtr publish                     # to the registry when logged in (gtr login), else as a git tag
gtr publish --git               # git push --atomic origin <branch> <tag>
gtr publish --registry <url>    # to another registry
```

`gtr version <bump>` writes the version to `gtr.json`, turns `## Unreleased` of
`CHANGELOG.md` into `## 0.1.1 — <date>`, commits both and tags the commit: `v0.1.1` for a
package at the root of its repository, `orm-mysql@0.1.1` for one in a subdirectory (the
tags `github:owner/repo/sub/dir#^0.1` installs from). The repository must be clean
(`--no-git` only writes the files, `--no-tag` does not tag). It warns about workspace
members whose ranges no longer accept the new version.

`gtr publish` checks that `gtr.json` has a name and a version and is not `private`, that
`dependencies` and `peerDependencies` have no `file:` or `workspace:` sources (nobody else
could install them), that the repository is clean, and that the tests pass (with the
`test.coverage` threshold; `--skip-tests`). To the registry it then checks that the version
is new and uploads the package: the files git does not ignore (all files outside a
repository), without `go.mod`, `go.sum`, `gtr.lock`, `gtr_modules/`, `node_modules/`,
`build/`, `.github/`, `.env*` (but `.env.example`) and test binaries, as a `.tar.gz`
(`--allow-dirty` publishes uncommitted changes). With `--git` (and without a registry login)
it checks that the version tag is on `HEAD` and that the remote does not have it yet, and
pushes the branch and the tag together.

## Link a local copy

```bash
cd ~/src/orm.go/core && gtr link      # register orm → this directory (~/.gtr/links.json)
cd ~/src/app && gtr link orm          # use it in this project
gtr link ../orm.go/core               # or by path, without registering
gtr link --list
gtr unlink orm                        # back to gtr.lock (gtr unlink: every link)
```

A linked package replaces every source of its name, like a workspace member, until
`gtr unlink`. Links are personal: they are kept in `.gtr/links.json` (added to
`.gitignore`), and `gtr.json` and `gtr.lock` do not change. `gtr ci` refuses to run with
links. For packages developed together all the time, a workspace is the better fit.

## Workspaces

A family of packages developed together (a core and its drivers) is a workspace
(ADR-0009): a root directory whose `gtr.json` lists the members.

```
orm.go/
  gtr.json            {"name": "orm-dev", "private": true, "workspaces": ["core", "drivers/*"]}
  core/               gtr.json {"name": "orm", "version": "0.2.0"}
  drivers/mysql/      gtr.json {"name": "orm-mysql", "dependencies": {"orm": "github:shibisty/orm.go#^0.2"}}
```

- **Members win.** Any dependency on a member's name — from the root, another member or a
  downloaded package, whatever its source — uses the member in place. The range must still
  accept the member's `version`. So a driver keeps its real source in its committed
  `gtr.json` (it must install on its own in CI), and inside the workspace it gets the local
  core with no edits. `"orm": "workspace:*"` (or `gtr add orm` in a member) names a member
  explicitly, for monorepos.
- **One install for everything.** `gtr install` anywhere in the workspace installs it from
  the root: one `gtr.lock` and one `gtr_modules/` at the root, members' `devDependencies`
  included, one version of each package for all members.
- **Generated files:** a `go.mod` in every member (and in the root if it has Go code of its
  own), and `go.work` at the root (`use` of every member, the `replace` directives). A root
  that only gathers members and overrides sources is not a module. Go tools and IDEs find `go.work` by
  themselves; scripts and the `go` shim run go with `GOWORK` set to it.
- **Commands in a member:** `gtr add`/`remove` change the member's `gtr.json`;
  `gtr run test` runs the member's script; `gtr run -r test` runs it in every member that
  has it, dependencies first.

Patterns are paths or one-level globs (`drivers/*`; `**` is not supported); `"!drivers/old"`
excludes. `gtr sync` in a workspace only regenerates the files (`--force`).

**Several families side by side.** A dependency of the workspace root overrides the source
of that name for the whole workspace, so a workspace can use a sibling folder's packages:

```json
{
    "name": "passport-dev",
    "private": true,
    "workspaces": ["core", "strategies/*", "sessions/*", "example"],
    "dependencies": {
        "orm": "file:../orm.go/core",
        "orm-redis": "file:../orm.go/drivers/redis"
    }
}
```

The directories are shared: a member keeps the `go.mod` its own workspace generated, which
also works when another workspace uses it as a `file:` package.

# Using gtr in CI

`gtr init --ci` writes `.github/workflows/ci.yml`: Linux, Windows and macOS × the lowest
and the newest Go that `engines.go` allows, gtr installed with `install.sh`/`install.ps1`,
then `gtr ci`, `go vet ./...` and `gtr test --coverage`. (It needs the gtr releases.)

Until then, or without the launcher, build gtr-manager from source and install the project
with it (full examples in the `ci.workflow.yml` of the orm, passport, migration and faker
repositories):

```yaml
env:
  GOPROXY: "off"        # go never downloads: dependencies are in gtr_modules
  GOWORK: "off"
  GOFLAGS: -mod=mod
  GTR_GOPROXY: https://proxy.golang.org   # where gtr itself downloads modules
steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-go@v5
    with: { go-version: stable }
  - name: gtr
    shell: bash
    env: { GOPROXY: "https://proxy.golang.org,direct", GOFLAGS: "" }
    run: |
      git clone --depth 1 https://github.com/shibisty/gtr-manager "$RUNNER_TEMP/gtr-manager"
      (cd "$RUNNER_TEMP/gtr-manager" && go build -o "$RUNNER_TEMP/gtr-bin/gtr$(go env GOEXE)" ./cmd/gtr-manager)
      echo "$RUNNER_TEMP/gtr-bin" >> "$GITHUB_PATH"
  - run: gtr ci          # or `gtr install` while there is no gtr.lock
    env: { GITHUB_TOKEN: "${{ github.token }}" }
  - run: go test ./...
```

# Package Sources

| Source | Example | Status |
|---|---|---|
| GitHub | `github:owner/repo#^0.1`, `github:owner/repo/sub/dir` | Supported |
| GitLab | `gitlab:group/sub/project#^0.1`, `gitlab:group/project//sub/dir` | Supported |
| Any git server | `git+https://host/repo.git#^1`, `git+ssh://git@host/repo.git//sub/dir`, `git+file:///srv/git/repo` | Supported (needs `git`) |
| Local directory | `file:../path` | Supported |
| External Go modules | `"github.com/go-sql-driver/mysql": "^1.10"` | Supported |
| Workspace members | `workspace:*`, `workspace:^0.2` | Supported (ADR-0009) |
| GTR registry | `"orm": "^0.1"` | Supported (gtr-registry) |

For GitHub Enterprise or a mirror set `GTR_GITHUB_API` (and `GTR_GITHUB_TOKEN` for its
token; `GITHUB_TOKEN` is only ever sent to api.github.com). Private repositories and
the GitHub API limit (60 requests per hour without a token) need a token:

```bash
export GITHUB_TOKEN=ghp_...        # PowerShell: $env:GITHUB_TOKEN = "ghp_..."
```

GitLab: `GTR_GITLAB_URL` (default https://gitlab.com) and `GTR_GITLAB_TOKEN` (or
`GITLAB_TOKEN` for gitlab.com), sent as `PRIVATE-TOKEN` to that server only. A GitLab
project path can have subgroups, so a monorepo subdirectory follows `//`.

`git+` sources run the `git` command: `ls-remote` lists the tags, one tag at a time is
fetched shallowly into `~/.gtr/cache/git`, and `git archive` exports it. Authentication is
git's own (credential helpers, SSH keys); gtr never waits for a password prompt.
`git+http://` is refused.

# Version Syntax

npm-style ranges (ADR-0004):

| Range | Meaning |
|---|---|
| `1.2.5` | exactly 1.2.5 |
| `^1.2` | `>=1.2.0 <2.0.0` (`^0.2` = `>=0.2.0 <0.3.0`) |
| `~1.2.3` | `>=1.2.3 <1.3.0` |
| `1.2` | `>=1.2.0 <1.3.0` |
| `>=1.0 <2.0` | explicit range |
| `*` | any stable version (or the default branch of an untagged repository) |

Pre-releases (`1.3.0-rc.1`) are selected only when the range names one.
